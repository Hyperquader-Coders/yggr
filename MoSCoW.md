# MoSCoW — yggr

Prioritisation by **Must / Should / Could / Won't have** (the lower-case Os just make it
pronounceable). This is the **scope** document, and it holds only what is **still open**: an
item leaves this file the moment it ships. Nothing here records work done — `git log` is for
that.

An empty band means that band is finished, not that it was never populated.

When an item ships, its reasoning is written into [`docs/DECISIONS.md`](docs/DECISIONS.md).

Where this file and [`docs/SPEC.md`](docs/SPEC.md) describe the same behaviour, SPEC is
authoritative — this is the schedule, not the specification.

## Must have

Empty. The MVP surface — diagnostics, hover, completion and formatting over a spawned
server — is implemented, and `make test` covers the headless client.

## Should have

- **Re-enable `appstream-compose`.** The manifest sets `appstream-compose: false`, so the
  bundle carries no composed AppStream index. The metainfo and icons are still installed and
  exported, but software centres read the composed data, and Flathub review expects it. This
  is a workaround for an upstream defect: `appstreamcli compose` runs inside the SDK, where
  gdk-pixbuf 2.44 loads images through a glycin loader that sandboxes itself with
  `flatpak-spawn --sandbox`. A build has no portal to spawn through, so every icon fails with
  `Loader process exited early with status '1'`. Upstream is gdk-pixbuf #292; its workarounds
  (downgrade gdk-pixbuf to 2.42, or rebuild it with `-Dglycin=false`) are changes inside the
  SDK and unreachable from a manifest.

  Ruled out, so nobody repeats it: the icons are valid at every size and all fail identically,
  `appstreamcli validate` passes on the metainfo, and the SVGs put `<svg>` at byte 39, inside
  the sniff window. `GLYCIN_SANDBOX_MODE=disabled` and `not-sandboxed` change nothing. Hand-
  composing the same staged tree against `org.gnome.Sdk//48` succeeds and against 49 and 50
  fails, so the defect arrived with 49.

  **Do not confuse this with the export-time icon check**, which failed the same build with
  `is not a valid icon: Format not recognized`. That one runs on the **host**, not in the SDK,
  and wanted librsvg's gdk-pixbuf SVG loader; the CI workflow installs `librsvg2-common` for
  it. Two failures, two machines — conflating them is what led to the runtime being pinned
  back to 48 for a while on a diagnosis that was wrong.

  **Next check: GNOME 51**, due around September 2026 and not yet on Flathub. The test costs
  seconds and needs no build: stage the metainfo, desktop file and icons in a directory, run
  `appstreamcli compose` against `org.gnome.Sdk//51`, and try `GdkPixbuf.Pixbuf.new_from_file`
  on one PNG and one SVG. If both pass, delete the `appstream-compose` line.

- **Filesystem access through portals instead of `--filesystem=host`.** Host access is MVP
  pragmatism — an editor has to see the user's files — but it is the broadest permission the
  Flatpak asks for and the one Flathub review will question first.

- **Build marksman from source.** It is the last prebuilt blob in the manifest, and
  Flathub review treats those as a submission blocker. It is F#/.NET 9 (`global.json` pins sdk
  `9.0.100`) and `org.freedesktop.Sdk.Extension.dotnet9` exists on Flathub, so the route is
  open — but a Flathub build has no network, so NuGet restore needs a `nuget-sources.json`
  generated by `flatpak-dotnet-generator.py`, pinning every transitive package by sha256 and
  regenerated on every marksman bump. Its vendored `LanguageServerProtocol` project and
  `MarkdigPatches` complicate the restore graph. Dropping marksman is the cheaper answer if
  Markdown LSP inside the bundle turns out not to matter.

## Could have

- **Submit to Flathub.** Distribution today is the amberlinux flatpak remote and the
  release bundle. Flathub is gated three deep: the composed appstream must exist, marksman
  must build from source (the entry above), and the
  Odin SDK extension must itself reach Flathub first — an app there cannot pull an
  extension from a third-party remote.

- **aarch64 Flatpak.** Needs per-arch `only-arches` variants for the marksman module, and an
  Odin SDK extension built against an LLVM that provides the AArch64 backend — llvm22 does
  not, so the compiler it ships reports arm64 as a missing target. That is the extension's
  problem, not this manifest's.

- **More bundled language servers.** The manifest carries a commented-out gopls module;
  Go module fetching would need `--share=network`, which the bundle deliberately does without.

- **Hover on a keybinding.** Hover rides GtkSourceView's own machinery, so it triggers on
  pointer dwell only (SPEC §4.3).

- **Restart a crashed language server.** A server that exits is reaped and LSP stays off for
  the session (SPEC §5); a bounded restart (say, once per minute) would bring it back without
  reopening the file.

- **Kill the server when yggr is SIGKILLed.** Window close and SIGTERM/SIGINT/SIGHUP shut the
  server down, but a SIGKILL cannot be handled and OLS does not exit on stdin EOF, so it is
  orphaned. `PR_SET_PDEATHSIG` needs a hook between fork and exec that `core:os`
  `process_start` does not offer.

- **A richer Odin language spec.** `data/language-specs/odin.lang` covers keywords,
  comments, strings and numbers; attributes (`@...`) and directives (`#...`) are not handled.

## Won't have (this time)

The MVP's protocol surface is exhaustive in SPEC §3, and it stays small — yggr is the test bed
where LSP features are prototyped before kat800 gets them, not a complete editor.

- Go-to-definition, references, rename.
- Code actions, semantic tokens.
- Incremental text sync — full-text `didChange` is fine at this size.
- Multi-root workspaces, and more than one server per buffer.
- Snippet-placeholder editing.
- A configuration UI.
- Full IBus/CJK input in the Flatpak. Simple IM keeps dead keys, compose and the emoji
  picker; **decided, not deferred** — revisit only if CJK input is actually needed.
